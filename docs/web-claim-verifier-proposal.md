## 1. Problem — a structural hole in the subagent family

The recurring task shape — "verify ONE atomic claim or technical constraint against the live web" (e.g. 「核验 NLB ENI conntrack 约束」) — has no dedicated executor. It arises in csr reconcile moments, in psv's single-claim fetch path, and in daily ad-hoc verification; today it falls to `general-purpose` with a short prompt and no verification contract, or to the orchestrator itself.

## 2. Why no existing agent covers it (contract citations)

| Agent | Contract (EXCERPT from its definition — ellipses mark cuts; quotes inside are character-exact) | Why it cannot serve |
|---|---|---|
| `solidforge:doc-reviewer` | "…reports schema'd doc-findings ONLY — never edits or fixes…"; tools Read/Grep/Glob | offline against cited/local sources only (it does flag claim-vs-cited-source conflicts); never fetches the external web |
| `solidforge:claim-verifier` | "…Given ONE atomic claim AND the fetched source text that adjudicates it, returns a verdict (verified / refuted / narrowed / unverifiable) grounded in a fetched-source quote…"; tools Read/Grep/Glob | the oracle text must be FED — it never searches or fetches |
| `solidforge:researcher` | "…Never judges conclusion truth — outcome axis, human only…" | has the web legs but is barred from adjudicating |
| `general-purpose` | (characterization — a CC built-in, no in-repo definition to quote; consistent with its use as the un-specialized fallback in docs/subagent-review-plan.md) | discipline depends on each caller's prompt hygiene |

The hole is deliberate-adjacent, not accidental: claim-verifier is offline BY DESIGN (its oracle is the fed text), researcher is non-judging BY DESIGN (bc's outcome-axis isolation). The missing fourth seat — search + fetch + adjudicate in ONE fresh context — was simply never defined. The counter "the orchestrator has web tools, verify directly" fails three ways: the orchestrator authored the artifact (stake bias — the same reason doc-reviewer exists as a fresh context), its context is scarce mid-loop, and discipline-as-default beats per-invocation self-restraint.

## 3. Decision

Build `agents/web-claim-verifier.agent.md` — plugin-level (csr and psv both live in-plugin; cross-project reuse), named by analogy to `claim-verifier` and `collision-verifier` — the family's two existing `X-verifier` ADJUDICATOR names (this agent adjudicates; `X-extractor` names are the extractors' pattern, not this one's). Altitude is the TASK SHAPE (web-grounded single-claim adjudication), not a domain — no `aws-verifier`.

## 4. Contract

- Mode selection: the CALLER states the mode — `claim` (an assertion to adjudicate; output = verdict) or `question` (a fact-shaped query; output = findings[]); absent an explicit mode, a checkable assertion defaults to `claim`, an interrogative to `question`.
- Role: given ONE atomic factual claim or fact-shaped technical question (+ optional version/scope context), search, fetch the adjudicating source(s), and return a verdict (claim mode) or grounded findings (question mode) — grounded ONLY in fetched text.
- Fresh context / no stake / read-only: did NOT author the artifact, has nothing invested in either verdict; reports, never edits or fixes (mirrors `doc-reviewer`'s phrasing).
- Tools: WebSearch, WebFetch, Read, Grep, Glob — built-ins only; NO user-scope MCP dependencies (plugin agents must stay portable). Read-only is enforced in FRONTMATTER like every READ-ONLY family agent (8 of 22 today — doc-reviewer, claim-verifier, researcher et al.; the write-allowing agents — implementers and others — lack the field BY DESIGN): `disallowedTools: Edit, Write, NotebookEdit` (the 6-of-8 common form; the fetch-BARRED extension (WebSearch, WebFetch added to disallowedTools) is carried by exactly TWO agents today — `collision-verifier` (the adjudicator) and `novelty-claim-extractor` (the extractor), the fetch-barred offline pair; `claim-extractor` carries no extension (no web legs to bar — tools Read/Grep/Glob only); `researcher` is the inverse case (web-legged, common form only — barred from writing, not from fetching); this agent must NOT copy the extension, its web legs are its mission).
- Oracle discipline: the fetched source TEXT is the oracle — never model recall. TWO rules with distinct provenance: (a) the exemplar's fetched-quote invariant, quoted exactly: "Your `evidence` for `refuted` / `narrowed` MUST be a QUOTE from the fetched text you were given — NOT model recall. A `refuted` / `narrowed` verdict without a fetched quote is INVALID: downgrade to `unverifiable`. …"; (b) THIS contract's own addition, by design — `verified` ALSO carries its grounding quote, because the output IS the evidence capture (an intentional, stated STRICTER-THAN-EXEMPLAR divergence: the exemplar's verified branch carries no quote because psv COUNTS verified claims as a bare integer and captures no per-verified-claim QUOTE anywhere — its packet quotes only refuted/narrowed claims, and its volatile-authority registry (per coverage-record.schema.json) records WHERE a VOLATILE source lived at run time (a path/location re-fetchability signal) for any claim adjudicated against one, verified included — a location record, still not a QUOTE; this contract instead captures the verified quote because here the output IS the evidence artifact (STRICTER on the corrected ground: the registry SIGNALS where a volatile source lived — a re-fetchability signal, never quote content)). `unverifiable` carries no quote requirement (nothing adjudicating may exist) — its grounding block: `quote` null; `url` / `fetched_at` / `source_tier` REQUIRED when a fetch was attempted but non-adjudicating, all-null allowed when zero fetches succeeded; the disclosure arrays carry what was tried. This STRICTER capture does not weaken the epistemics — the exemplar's caveat below is the checked-instance discipline that keeps the stronger output honest: "**Comparison blind-spot caveat (workspace rule 3):** `verified` means YOU found no contradiction in the fetched text — NOT that none exists. The fetched source is strongly decoupled; your comparison is not. `refuted` / `narrowed` additionally involve a bounded interpretive step. State this honestly." Route the caveat to the output's `note` slot — mirroring claim-verifier's `note`.
- Source tiers: `source_tier` is researcher's provenance enum VERBATIM (family-shared vocabulary): `official-spec | peer-reviewed | vendor-doc | blog | unknown` — preference ordering official-spec > peer-reviewed > vendor-doc > blog > unknown; `unknown` labeled honestly, never silently mapped. (tier boundary, this contract's definition: `official-spec` = the NORMATIVE document issued by the authority governing the artifact — the vendor's official product docs for a product, the RFC/standard page itself for a protocol; `peer-reviewed` = independently refereed LITERATURE about it — journals, conference papers, published analyses. So an RFC is `official-spec`, not `peer-reviewed`; `vendor-doc` = vendor-published material that is NOT the normative artifact document — release notes, support KBs, engineering posts. First-party vs community blogs both = `blog` — the distinction is NOT a schema field (the enum stays 5-value); the URL itself is the reader-visible distinction. Preprints (not-yet-refereed server posts, e.g. arXiv) map to `blog` — the URL carries the server identity. Dual-venue tie-breaker: when the same adjudicating work has both a preprint and a published-venue URL, cite the highest-preference-tier URL that was actually FETCHED (a fetched arXiv copy with an unfetched published URL stays `blog` + the published URL noted in `searched`). Mapping sources onto the EXISTING five values is this contract's own interpretive layer; EXTENDING the enum (adding a sixth value) would be a family-wide decision, not this contract's.)
- Volatile-fact hard gate: quota/default/limit-class facts (conntrack bounds, API defaults) MUST carry a fetch date + version anchor; the gate guards POSITIVE confirmations — a `verified` on a volatile-class fact without both is INVALID output (question mode: an `unanchored volatile-class element can never be grounded` is the same rule); `refuted` / `narrowed` already carry their limiting text and quote, and the fetch date always rides in the grounding block — downgrade with a selection criterion (not either/or): `narrowed` when the fetched text grounds the claim only as of its own date/version — a weaker, time-scoped support than a version-anchored `verified` (stated in this contract's own terms; claim-verifier's `narrowed`-as-weaker-form is the adjacent analogy, not identical semantics), `unverifiable` when no anchorable source was found at all (mirrors claim-verifier's invalid-output rule). Enforcement honesty (rule 3): this is enforced in the agent's own contract (self-declared downgrade, like claim-verifier's quote rule) and outer-ring checkable via date/anchor presence in the output — NOT a deterministic self-gate (LLM output has no local validator; deterministic enforcement would require adapting psv's EXISTING fetched_quote_gate (PSV-I5(a), skills/primary-source-verification/infra/test/fetched_quote_gate.py) to this agent's output shape — the harness exists today; the adaptation is the future option).
- Bounded search: ~5 searches / ~8 fetches per task — claim OR question (advisory budget stated in the agent contract — same enforcement class as the volatile gate: self-declared + outer-ring checkable via the `searched` disclosure, not a deterministic gate); on exhaustion (claim mode) return `unverifiable` with what was tried; on exhaustion (question mode) emit `findings[]` reflecting what was tried with every element at `confidence: unresolved` — never hunt unbounded (a plain bounded-budget doctrine; ADR #52's bounded+observable SUBSTRATE budgets are the adjacent precedent, not the same mechanism).
- Output schema (family norm — fenced JSON ONLY, exact fields): a ```json block with `claim_id` (REQUIRED in CLAIM mode — echo the caller-supplied claim id, mirroring claim-verifier; ABSENT in question mode, which has no claim id), `verdict` ∈ {verified, refuted, narrowed, unverifiable} — the LABELS re-used verbatim from the exemplar (psv inherits them via PSV-I3); semantics mirror the exemplar fully — `narrowed` keeps its generic supports-only-a-WEAKER-form meaning (the volatile-gate downgrade produces narrowed's TIME-SCOPED form, one instance of the generic semantics, not a replacement of it): a grounding block (`quote` verbatim from the fetched text — null for `unverifiable`, per the oracle-discipline rule; `url`, `fetched_at` date, `source_tier`), `searched` / `not_found` (coverage disclosure), and `note` (REQUIRED for `verified` verdicts — carrying the blind-spot caveat; optional otherwise — a stated divergence from claim-verifier's always-optional `note`; T1's agent contract must render it in its fenced JSON sketch as `note: "<REQUIRED for verified — the caveat; optional otherwise>"`). Multi-fetch collapse (claim mode): the grounding block cites the fetch whose text DETERMINES the verdict (tier preference breaks ties only among determining fetches); every other fetch is listed in `searched`. Question mode: EACH finding's grounding block cites its own determining fetch the same way; fetches feeding no finding are listed in `searched`. For `verified` there is NO `finding` sub-object; for verdict ≠ verified a `finding` sub-object is REQUIRED, mirroring claim-verifier's shape verbatim (`defect_id`, `severity`, `kind`, `location`, `evidence`, `suggestion`). Question mode (this contract's OWN extension — the exemplar is per-claim verdict only, no question shape anywhere in the family): NO top-level `verdict`; a `findings[]` array whose every element carries the grounding block (`quote`, `url`, `fetched_at`, `source_tier`) — present on every element, its fields MAY be null for `unresolved` plus a per-finding `confidence` ∈ {grounded | partial | unresolved} — DEFINED: `grounded` = the quote directly answers the question; `partial` = the quote answers a weaker/scoped form, or the source lacks a version/date anchor — the two states distinguished by a `partial_reason` sub-field (`scope` | `unanchored`; the volatile gate's question-mode wiring sets `unanchored`: an unanchored volatile-class element can never be `grounded`); `unresolved` = no fetched text adjudicates — an `unresolved` element MAY carry `null` grounding fields (no fetch adjudicated); the disclosure arrays carry what was tried; top-level `searched` / `not_found` are REQUIRED in both modes (both fields, empty array allowed). Severity mapping into doc-findings packets follows claim-verifier's rule verbatim: refuted→blocker, narrowed→warning, unverifiable→coverage — and the KIND mapping (csr's doc-findings packet schema requires kind ∈ {contradiction, authority-chain-break, scope-creep, structural-gap, citation-error, coverage-gap} — a DIFFERENT receiving schema from psv's packet, where claim-verifier's own kind enum claim-refuted|claim-narrowed|claim-unverifiable lives): claim-mode refuted→`contradiction` (the claim conflicts with the fetched source — the schema's own contradiction gloss), narrowed→`authority-chain-break` (gloss-exact: the doc asserts more than the fetched source says — the source does not say what the doc says), unverifiable→`coverage-gap`. (The kind choices are OWNED against the schema's glosses.) These mappings apply to CLAIM mode only (question mode has no verdict to map). Question-mode confidence → doc-findings severity (the CONVERSION rule — it governs only which elements become doc-findings PACKET entries, never the output itself): findings[] IS the answer set and holds elements of EVERY confidence level (a `grounded` element is the ANSWER, not a defect — it converts to NO packet entry, the informational analog of claim-verifier's counted-not-listed verified); `partial` → `warning` packet entry (kind `authority-chain-break` — gloss-ADJACENT: the source does not say what the question demands, the question-for-doc instantiation of the gloss's "does not say what the doc says"); `unresolved` → `coverage` packet entry (kind `coverage-gap`). Evidence-capture clarification: the QUOTE/URL/DATE block of the output is what drops into a run-dir `evidence/` file (the record's excerpt portion), mirroring the incident precedent's bare-excerpt shape.
- Boundaries: adjudicates atomic factual claims or fact-shaped technical questions ONLY; never judges whether the doc's thesis/conclusion is right (outcome axis stays human — family philosophy). Does not replace psv's authoritative full-M pipeline; it is a single-claim building block.
- No hardcoded model or max_turns (workspace convention).
