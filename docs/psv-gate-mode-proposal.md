# psv Gate Mode — Proposal (psv-subset-gate → csr → psv-full)

> Status: **Proposal (csr-CONVERGED 2026-08-10 — substantive_converged=true, 2 rounds, 9/9 core claims; record at docs/psv-gate-mode-proposal.csr-record.json).** Ready for the enumeration-update implementation (iteration plan at docs/psv-gate-mode-iteration-plan.md). Refines the psv insertion point in the pipeline-order enumerations: when rule-13 conditions hold, run psv FIRST as a cheap load-bearing-claims gate (GO/NO-GO), then csr, then psv again as the authoritative full-M record on the stabilized doc. Born from the psv-first vs csr-first discussion (2026-08-09): the order decision is claim-set stability + dominant error type; the redundancy is only worth paying when the gate is cheap (subset) and the doc is citation-heavy.
> Scope: pipeline-order enumerations + psv positioning text. NOT a code change to psv/csr infra. Does NOT overturn psv ADR #1 (single extract→fetch→verdict→coverage pipeline, NOT a debate loop) — the gate is the same pipeline FAMILY run twice (subset then full), not a loop — with gate-specific configuration: subset extraction, grouped-by-source verification (the cost optimization the dogfood used; full psv keeps per-claim fresh context), and a batch GO/NO-GO aggregation instead of the full coverage disclosure (N06).
> This document goes through csr → psv → bc → pd. psv on THIS document: SKIPPED per CLAUDE.md rule 13 (csr alone suffices when citations are low-stakes/local) — all citations are local files (enumeration lines, ADR texts, the gate record) that two csr rounds read and quoted per-claim; the gate-mode evidence ran psv on the experiment subject instead (docs/psv-gate-dogfood.gate-record.json).

## Context — the order decision

- The canonical order is `csr → psv → bc` (USER_GUIDE § Two-axis; CLAUDE.md rule 13): psv is additive, inserted after csr, before bc freezes.
- Two variables decide the better order (discussion 2026-08-09):
  - claim-set stability — psv is per-claim (extraction binds location + expected source); any operation that restructures the doc must precede it, or the M set and verdicts go stale
  - dominant error type — csr catches structural fact errors (internal contradiction, authority-chain-break, citation-error, enumeration/census errors); psv catches claim↔fetched-source fidelity
- csr-first is right for authoring-type docs (majority): csr's rounds stabilize the claim set, psv verifies once at the end.
- psv-first is right for (a) review-type docs with stable structure, (b) a GO/NO-GO premise gate before investing in csr rounds — the residual "waste on wrong premises" risk.
- Full double-psv is rejected: the first full-M run pays per-claim cost on an unstable claim set, and two different-M coverage records cannot be merged by a reader (P61-style misparse confusion doubles — P61 = the refuted claim in the fix-plan psv record that was an extractor misparse, not a doc error).

## Proposed design

```
psv(core-claims subset, GO/NO-GO gate) → csr (structural convergence) → psv(full M, authoritative record)
```

- **Gate (first psv)**: extract/verify ONLY the load-bearing claims — a standalone list produced by psv's own frame step (SKILL.md step 1); this list BECOMES csr's core-claims frame (reuse runs gate→csr, NOT csr→gate — csr's frame does not exist before csr runs; the dogfood evidence exercised the standalone branch). Verdict summarized as a batch signal with an EXPLICIT rule (PSVGM-02): **NO-GO iff any load-bearing claim is refuted OR unverifiable, OR ≥2 load-bearing claims are narrowed; GO otherwise** — non-goal restated (N10): the gate NEVER extracts non-load-bearing claims, so no non-load-bearing verdict can flip the batch. NO-GO action is differentiated by verdict class (N05): REFUTED load-bearing → hand back to the AUTHOR for source rework; UNVERIFIABLE load-bearing → VERIFIER-side re-fetch first (full-text fetch may resolve it, as G4/G5's abstract-limited status suggests), and only rework if the re-fetch confirms the gap; NARROWED ×≥2 → author rework of the narrowed citations. Re-verify loop (gate-6 boundary): after rework/re-fetch, ONLY the affected claims are re-run through the gate (cheap subset pass) before any csr investment — a re-gate is required to re-establish GO. This is bounded iteration, NOT a debate loop: re-gates are capped at 2 (2 failed re-gates → escalate to human), the re-gate verifies only the reworked claim set (no adversarial rounds, no fresh full extraction), so psv ADR #1's single-pipeline-not-debate-loop boundary stays intact and checkable. GO → proceed to csr. This rule fits the recorded evidence: G5 (load-bearing, unverifiable) → NO-GO with 0 refuted.
- **GO signal contract (PSVGM-09)**: GO is a PREMISE signal on the core claims only — explicitly OUTSIDE psv ADR #3's "sole top-line signal is `oracle_verified_under_known_coverage`" contract. The gate record is a gate record, not a coverage record; the authoritative coverage disclosure comes only from the second (full-M) psv.
- **csr**: unchanged (structural convergence).
- **Authoritative record (second psv)**: full-M per-claim verification on the stabilized doc — the ONLY `oracle_verified_under_known_coverage` record a reader trusts. The gate run is NOT conflated with it.
- **Trigger conditions** = CLAUDE.md rule 13 conditions exactly (load-bearing citations + fetchable sources + wrong citation materially weakens the argument). No new trigger machinery beyond the ODP-5 decision (N02): if ODP-5 resolves to a quantified rule, that rule IS the trigger refinement — line 27's 'no new machinery' is then scoped to the gate itself, not the trigger.

## Risks and mitigations

- R1 — gate conflation: a reader treats the gate's GO as a verification pass. Mitigation: ODP-3 — distinct record status + wording ("GO/NO-GO batch signal, not a coverage record").
- R2 — double-per-claim cost creep: the gate grows from subset to full M. Mitigation: gate scope = the standalone load-bearing list (which becomes csr's frame), stated as an upper bound in the guide.
- R3 — gate false-NO-GO: a draft with churn-y sources gets blocked before csr can fix the doc. Mitigation: the batch rule is explicit (adv-2): a single NARROWED claim does not NO-GO (the ≥2-narrowed-on-load-bearing threshold flips); refuted or unverifiable LOAD-BEARING claims always flip. (The earlier "single refuted does not NO-GO" wording conflicted with the explicit rule — corrected; within the gate, M is load-bearing by construction.)
- R4 — evidence experiment selects an unrepresentative doc. Mitigation: the dogfood doc must be a REAL citation-heavy artifact, not synthetic — own or external. The executed subject is disclosed as external: fedaot-kb `docs/retrieval-memory-evaluation.md` (outside solidforge; read-only) — real and non-synthetic, satisfying the mitigation's intent (adv-6).
